## Reading engine state

`GET /health` is unauthenticated; `/props` and `/v1/models` need the bearer key; `/stats`, `/server_info`
and `/version` do not exist (404) — `/props` also reveals the live sampling in
`default_generation_settings.params`, plus the served pack's identity: `model_path` (the dense-GGUF filename names the family/repo — `qwen-nvfp4-gptq-dense.gguf` = Maximilian228 NVFP4-GPTQ-Strata), `model_alias` and `build_info`; answer 'which model is serving?' from that evidence, never from memory. `strata.log` in the install dir is the source of truth — per-request decode/prefill rates,
expert-cache hit rate, tier residency, startup decisions.

```bash
grep -o -E 'prompt [0-9]+ tokens = .* generated in [0-9]+ ms \([0-9.]+ tok/s\)' strata.log
```

Bucket decode speed **by context size** before judging performance — one median hides the shape
(same engine: ~48 t/s short, ~57 mid, ~50 at >80K).

## Live decode probe (no benchy, ~1 min)

Fast "how fast is decode right now" check: POST `/v1/chat/completions` (bearer key required even
from localhost; temperature 0, `enable_thinking: false`, `max_tokens` ~400), t/s =
`usage.completion_tokens` / wall seconds. Temperature 0 sirve SOLO para throughput bruto (los tokens
cuentan igual caigan en el bucket de respuesta que caigan) — NUNCA saques conclusiones de
comportamiento (verbosidad, bucles, ausencia de respuesta) de una sonda greedy: repite a T1.0/0.95/20
(la temperatura viva) antes de afirmar nada sobre cómo el modelo «piensa». Run ≥3 and judge the median — the FIRST run after idle
reads ~35% slow (cold MTP draft-suffix caches and page tables; measured 58-62 vs 91-95 warm).
Warm short-context baseline of this box: 91-95 t/s (spec4/b42, 2026-10-24 morning); 95-102 t/s
(spec6/b46, 2026-10-24 evening — live config).

## Large pages: does NOT apply in low-RAM mode

`enable-large-pages.cmd -Check` saying **ACTIVE** does not mean the engine uses them. The
`large pages (2097152 B)` log line belongs to the **expert arena** path, which only runs with 96+ GB
installed. With 64 GB the engine logs `low RAM (below 96 GB installed)` + `experts via mmap
(--mmap-experts)` + `FileExpertSource: ... page-locked and mapped` — that path never touches the
arena, so the message is absent **by design**, not a failure. Absence of `error 1314`/`1450`
confirms the privilege was never refused. Never claim "large pages didn't apply" from the missing
line alone: check installed RAM and which mode the log shows.

Even when it applies, the project's `docs/NVFP4.md` caps its value: it stabilises the CPU pool at
~7.5 ms/round (vs 7.4–11 wandering) but *"decode itself is GPU-bound, so the rate barely moves"*.
Never promise a throughput jump from large pages.

## VRAM headroom

```
strata serve: 252 MiB of VRAM free with everything loaded - LOW: requests may stall;
add --vram-reserve-mib 960 to the config's args (or lower --max-context)
```

`--max-context` 262144 → 131072 frees ~5 GiB KV and buys ~+25% expert slots. Check the user's real
session depth in the log first (Raúl's reach ~94K, so 131072 fits but is tight).

## What actually bottlenecks a 64 GB / 8-core box

The engine spawns **7 expert-pool workers + host thread** → an 8-core CPU (7800X3D) is the limit,
not RAM or PCIe (measured 57.9 GB/s Gen5; the RAM kit is DDR5-6000 CL30 EXPO-ON (Corsair CMH64GX5M2B6000Z30) — CIM `Speed: 4800` is the JEDEC-SPD max, the live clock is `ConfiguredClockSpeed: 6000`, a known WMI quirk with XMP kits on Ryzen; verified 2026-10-24). Bandwidth is therefore ≥ the repo reference machine's DDR5-5600: the remaining gap (91 vs ~115 t/s low-RAM mode) is CORES, not RAM; measured platform factor ~0.79). Reference 138 t/s figures come
from a 16-core 9950X3D. With 64 GB, ~25 GiB of experts stay on SSD (`blob reads from the file`);
128 GB is the only change that removes that tier — and it also unlocks the arena path where large
pages finally apply.

**CPU-upgrade decision (2026-10-17, Raúl): PAUSED until Qwen4's lineup is known.** A 16-core
(9950X3D, ~709€ PCComponentes; X3D2 dual-V-Cache ~949€ Caseking — its second cache is worth ~0 for
Strata) is worth an estimated +15-30% decode ONLY in the MoE-streamed-from-RAM branch; a dense
tier-27B-class Qwen4 runs fully on the 5090 and makes the CPU irrelevant, and a bigger MoE tier
would make 128 GB the real gate. Free pre-check before any purchase: restrict strata.exe core
affinity and measure decode scaling (if flat below 8 cores, more cores won't help). PITFALL
(tested 2026-10-24): the affinity pre-check CANNOT run from WSL interop — strata.exe is elevated,
the WSL-launched powershell is medium-IL, `ProcessorAffinity` throws "Acceso denegado" even after
enabling SeDebugPrivilege (lasterr 1300 = privilege not held). Run it from the elevated Windows
PowerShell that manages Strata: `$p=Get-Process strata; $p.ProcessorAffinity=0xFF` (half), measure
decode via /v1/chat/completions, restore `$p.ProcessorAffinity=0xFFFF`.

## Cold-boot vs post-video speed: the RAM budget lever (solved 2026-10-10)

Strata's low-RAM budget is decided from **RAM free at the moment of engine start** (`available − STRATA_RESIDENT_HEADROOM_GIB − 0.25 GiB margin`), so a cold boot (apps, AV, NVIDIA loaded) got 26-38 GiB (~40-55 t/s) while a broker relaunch after a video (Windows had reclaimed memory) got 42-45 GiB (~70-90 t/s). Fix, in `config/cocobot.json` (the single start path for cold boot AND broker relaunch — put engine args there, not in start-hermes.ps1): `--ram-budget 46` in args + `STRATA_RESIDENT_HEADROOM_GIB: "2"` in env. 46 still clamps to whatever is free at boot — the point is removing the low ceiling. Final result after also trimming Windows autostarts (Edge session-start, Docker, WebUI off) + a working-set trim (`EmptyWorkingSet` via Add-Type psapi, deny-list of critical procs) in start-hermes.ps1 right before launching Strata + `.wslconfig memory=20GB`: boot-available went 44.64 → 47.75 GiB, budget 45.50 GiB > the 44.30 GiB of experts outside VRAM = **all experts page-locked from cold boot, file tier effectively gone**; cold-boot decode 75-85 t/s, prefill ~4470 t/s. Nothing left to gain from RAM on 64 GB — next step is 128 GB hardware. A `WARNING: the RAM budget cannot be kept` (vs the normal clamp line) means boot was crowded — drop to 44.

The `--prefill auto:16384` → `auto` change: `auto` picks the largest chunk the cache can lend (32768 on this box), NOT one that fits the RAM budget — the `only 0 of their experts fit` warning persists with either setting in low-RAM mode (its "or auto" advice doesn't hold here). Judge by measured PP t/s instead: `auto` gave 4979 t/s incremental, top of the historical range (auto:16384 median was ~3270). The warning is cosmetic; the log line `prompt N tokens = R reused + M read in X ms (PP t/s)` is the truth.

## Crash loops: OOM on checkpoint restore / image upload (2026-10-11)

Symptom: `image position upload failed` → `restoring a conversation checkpoint failed` (log: `checkpoint restore ... out of memory`) → exit 1 → restarts fail with `prefill gemm: cublasCreate: cuBLAS status 1` (`only 0 MiB free once the slots are written`). Cause: RAM (~2.3 GiB free with ram-budget 46) + VRAM (~349 MiB) both at the edge. Fixes applied: page file FIXED 65536 MB (engine's own warning; system-managed fails, issue #60) + `--vram-reserve-mib 1024` (→794 MiB free, 7320 slots) + mmproj bf16. (These cured the mid-session OOMs; start failures are a separate problem, see next section.)

mmproj bf16: `mmproj-orca-f32.gguf` is a bf16 upcast (lower 16 bits zero in every tensor). Convert only 2D weights; keep pos/patch/embd tensors F32 or strata-vision asserts `GGML_TYPE_F32` and server says `the vision encoder stopped`. Script pattern: gguf-py reader→writer via `uv run --with gguf --with numpy`. Test encoder standalone: pipe `ENC <img> <out>` to `strata-vision.exe --mmproj .. --model ..` (expects `OK ...`); bf16 vs f32 embeddings cos 0.99985. The server relaunches the vision subprocess on next request (an `OSError Errno 22` traceback on stdin write after a crash is cosmetic). PNG via curl needs no Pillow; synthetic test PNG must be real (make with `uv run --with pillow`).

## Start failures: `prefill: host buffers or events for a chunk` / `cublasCreate status 1` / `relayout: the stream failed`

Also `prefill: the token id buffer (out of memory)`. Root cause is NOT settled — do not announce a fix before a clean start proves it. Ruled out by evidence: free RAM after the copy (failed with 6.5-6.9 GiB available), engine version (0.1.40.3 failed the same way as 0.1.42), `--prefill auto:16384`, more `--vram-reserve-mib` (failed with 964 MiB free). Observed pattern: first start after a Windows reboot usually works; once the engine crashes, every retry fails until reboot (pinned-memory state degrades) → advise reboot rather than retry loops. Correlates with page-locked complement ~44.5 GiB (≤42 GiB never failed historically) and appeared after a Windows cumulative update. Current lever under test: `STRATA_RESIDENT_HEADROOM_GIB` 6 (budget = available − headroom, so pinned shrinks to ~42-43 GiB) on latest engine.

Diagnosis procedure (do this BEFORE changing config; each blind config flip cost a reboot cycle):
1. Tabulate every start in strata.log: `awk` over `engine started` / `session is up (engine X)` / `pinned cache complement ready: resident N` / `re-checked ... X GiB available` / `only N MiB free once the slots` / first error vs `VRAM free with everything` (OK). Compare by version, pinned GiB, free RAM, free VRAM, and time since reboot.
2. Check `Get-Process strata*` + port 8097 + nvidia-smi for leftovers; check Setup/System event logs for updates near the first failure.
3. Change ONE variable, and tell Raúl it's a hypothesis, not a fix.
When the window closes instantly: the server gives up after 3 failed engine starts; the cause is in strata.log, the user need not catch it on screen. Engine swap = replace `engine/` + `serve/` + `release-manifest.json` together (backups `backup-<ver>-<date>/` next to the install; release zips via `gh release download -R sergqwer/strata-nvfp4`); expert-profile.bin is identical across 0.1.40-0.1.42. Upstream refs: Niko1221/Strata#1756 (failed cudaHostAlloc kills engine on 64 GB host), PR #1498 (cudaHostRegister fallback, not merged), sergqwer/strata-nvfp4#6 (Windows cudaHostAlloc refused ~1 GiB). ## Images and "the prompt gets reprocessed" (diagnosed 2026-10-13, fix under test 2026-10-14)

Pipeline internals and a live prefix-reuse measurement recipe: `references/vision-prompt-reuse.md`.

- **Images themselves do NOT break prefix reuse.** The serve layer (`Vision` in `serve/server.py`) caches image embeddings by SHA-256 of the bytes (64 entries, files under `%TEMP%\strata-vision-*\*.sve`), so a byte-identical resend never re-encodes; the engine validates image identity on checkpoint restore (`checkpoint image prefix differs`) and a turn adding a new image reads only the image's own tokens (~30–1000, live-verified). If the main session shows `0 reused` after an image turn, look elsewhere before blaming the image.
- **The real reread cause is checkpoint eviction by other conversations.** `--prompt-cache 6` (default) is shared across ALL conversations: a one-shot (~1.2K tokens, logs `1 checkpoints` — background_review/compression) evicts the main session's checkpoints, and the next main turn logs `0 reused + ~50000 read in 14-17 s`. Engine restarts (each `engine started` line) likewise drop every checkpoint. Diagnose by tabulating `prompt N tokens = R reused` lines around one-shots/restarts, NOT by looking at image turns.
- **`strata_checkpoint: false` (`ckpt=0`) does NOT fix it — measured.** The flag works at the engine level (one-shot logs `0 checkpoints`), but the decisive A/B (main ~45K → one-shots → main) shows the main turn still gets `0 reused + 45K read in ~11 s` even when the interleaved one-shot is a single 62-token call with `ckpt=0`: ANY interleaved conversation breaks the main chain, regardless of whether the one-shot stores checkpoints. Do not re-propose ckpt=0 or a bigger `--prompt-cache` for this — the mechanism is chain breakage, not slot count.
